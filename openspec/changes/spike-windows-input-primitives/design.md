## Context

See `proposal.md` — Why. Three Win32 assumptions underpin ADR-0003, ADR-0004, and
ADR-0009, and none has been executed on this machine.

The relevant constraint on how these are built: a spike's value is the answer, not the
code. Code written to answer a question tends to survive into production by accident,
carrying assumptions from a throwaway context. These are deliberately structured so that
cannot happen — they are separate `cargo` projects, not workspace members, and nothing in
the product ever depends on them. The one artifact that does survive is data (layout
fixture JSON), not code.

## Goals / Non-Goals

**Goals:**

- Answer three yes/no questions with observed output, not reasoning.
- Produce frozen `uk`, `en_us`, `de` layout fixtures for `lexiswitch-core` tests.
- Settle the `windows` crate feature set that `lexiswitch-win` will inherit.
- Where an answer contradicts a recorded ADR, produce a superseding ADR.

**Non-Goals:**

- Reusable abstractions. Each spike is one file, and duplication between them is correct.
- Error handling beyond what is needed to see the result. `unwrap` is fine here.
- Any product code. `lexiswitch-core`, `lexiswitch-win`, and `lexiswitch` do not exist at
  the end of this change, with the sole exception of the fixtures directory.

## Decisions

**Standalone `cargo` projects under `spikes/`, not workspace members.**
A workspace member is one `Cargo.toml` edit away from being a dependency, and spike code
carries assumptions that were never meant to ship. Keeping them outside the workspace
means `cargo build` at the root cannot compile them and `cargo test --workspace` cannot
run them. Alternative considered: feature-gated modules inside `lexiswitch-win`. Rejected
— it makes the boundary a flag rather than a fact, and flags get flipped.

**Findings recorded in `docs/spikes/`, separate from ADRs.**
A spike records *what was observed*; an ADR records *what was decided*. They have
different lifetimes — an observation stays true, a decision can be superseded. Mixing
them means the ADR log accumulates measurement detail nobody needs when reading for the
decision. The findings doc is the evidence an ADR cites.

**Spike 3 runs first, and blocks the others on failure.**
It is the only one whose failure invalidates a decision outright: a negative result means
ADR-0004's runtime-derived tables are not viable and the layout strategy must be
redesigned. Spikes 1 and 2 produce limitations or parameter values, not redesigns. There
is no value in learning hotkey timing for a design that is about to change.

**Fixture format is JSON, generated once and committed.**
`lexiswitch-core` forbids Win32 by design (ADR-0001), so its tests can never call
`ToUnicodeEx`. They need frozen data. JSON over a Rust source table because the file is
generated by a tool and read by tests — neither party benefits from it being code, and a
committed data file makes a layout change visible as a data diff in review.

**Dead keys are recorded as dead, not resolved.**
Where `ToUnicodeEx` reports a dead key, the fixture marks that position as dead rather
than storing whatever character a subsequent call produced. A dead key has no single
character, and inventing one would put a wrong answer into the fixture that every later
test then treats as ground truth.

## Risks / Trade-offs

**`ToUnicodeEx` dead-key state corrupts subsequent probes silently.** → The known failure
mode: probing German `^` leaves state pending, and the *next* probe returns a combined
character with no error. Spike 3 must flush between probes (call with a known non-dead key
and discard, or clear via the documented double-call) and must verify the flush works by
probing a dead key deliberately and confirming the following probe is unaffected. A spike
that does not test its own flush proves nothing.

**Spike 1 needs an elevated window to test against.** → Requires launching an elevated
Notepad or Terminal and typing into it, which is a manual step and cannot be automated in
the spike itself. The spike prints observed events; the human confirms whether keystrokes
from the elevated window appear.

**A spike answers on one machine, with one set of layouts installed.** → Findings are
specific to this hardware and this configuration. That is acceptable — the product has one
user on one machine — but the findings doc states the machine configuration so a future
reader knows the scope of the claim.

**`WM_HOTKEY` timing may prove usable but imprecise.** → If timestamps resolve to a
granularity that makes 500 ms boundaries unreliable, the answer is a different default
window rather than a design change. Spike 2 reports the observed granularity, not just a
pass/fail.

**Spike code is quality-exempt, and that only holds if it stays outside the workspace.** →
The exemption is enforced structurally, per the decision above, not by intent.
